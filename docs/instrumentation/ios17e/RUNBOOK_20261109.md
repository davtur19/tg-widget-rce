# iPhone 17e test runbook — USB recovery and instrumentation (2026-11-09)

Target: iPhone 17e `iPhone18,5`, iOS 27.0 build `24A437`, UDID `<UDID>`,
stock Telegram 13.2 (36535), bundle `ph.telegra.Telegraph`. The parser 0day is
device-proven once (message 5725, `rce.txt` = `RCE_OK\n`); the gated twin and
the two-phase handshake remain host-only.

This is the operational runbook: how to recover the USB link, how to drive the
stock app, how to read the markers, and the known chat-scroll limitation. The
original engineering logs are
`vulns/0day-2-RCE-PARSER-SCOPE/IOS27/evidence/instrumentation-plan.md` and
`notes/ios17e_instrument_20261108.md`; the current reliability matrix is
`lab/ios17e/reliability_20261109/MATRIX.md`.

**One device operation at a time. No other agent touches the phone while a
run is in progress.**

## 1. Identify the right device

Do not confuse the 17e with the 6s.

- 17e: `iPhone18,5`, iOS 27.0 `24A437`, UDID `<UDID>`, USB `05ac:12a8`,
  `bcdDevice=18.05`.
- A LAN `_rdlink._tcp` / mDNS entry can belong to the older 6s even when the
  17e is the target. Always confirm `ProductType=iPhone18,5` and the UDID in
  `usbmux list` before using a network transport.

Useful checks:

```sh
VENV=<HOME>/ailocal/Telegram/ios_sideload/venv/bin
$VENV/pymobiledevice3 usbmux list
lsusb | grep -i 05ac
$VENV/pymobiledevice3 doctor
```

Expected: one JSON entry with `ProductType=iPhone18,5`,
`ProductVersion=27.0`, `BuildVersion=24A437`.

## 2. Host environment

- `pymobiledevice3` 11.49.2 in `VENV`; DDI 642.4 is normally already mounted.
- OCR (`rapidocr_onnxruntime`) is in the **venv**, not the system Python. Use
  `$VENV/python` for `ocr_screenshot.py` / `navigate_chat.py`, otherwise you
  get `ModuleNotFoundError`.
- Bot token: `~/.config/tgbot/token.env`, variable `TG_BOT_TOKEN`. Never print
  or commit it.
- CoreDevice commands use `--userspace` on this host (no root tunnel needed
  for the CLI operations used here).
- Close stale forwards/attachments before recovery:
  `pkill -f 'pymobiledevice3 usbmux forward'`; `pkill -f '/idund'`.

## 3. USB bug: symptoms, cause, recovery

### Symptoms

- `lsusb` shows `05ac:12a8` (the phone is physically on the bus), but
  `pymobiledevice3 usbmux list` returns `[]` or alternates between the device
  and `[]`.
- `pymobiledevice3 doctor` reports: the host sees the iPhone, usbmuxd does
  not; "fix: restart the usbmux daemon, make sure the device is unlocked and
  trusted".
- usbmuxd can activate the device (USB config flips 3→4, ipheth binds) but
  the lockdownd preflight fails, so usbmuxd 1.1.x never lists it.
- After a stale forward/Frida/attachment session, the phone-side mux can STALL
  every usbmux packet (`ReadBUID`/`ListDevices`/`Connect` → pipe error).

### Recovery (documented procedure)

```sh
VENV=<HOME>/ailocal/Telegram/ios_sideload/venv/bin
UDID=<UDID>
$VENV/python tg-rce/docs/instrumentation/ios17e/usb_recover.py \
  --attempts 3 --udid "$UDID" --pymobiledevice3 "$VENV/pymobiledevice3"
```

The script:

1. kills stale `pymobiledevice3 usbmux forward` and `idund`;
2. stops usbmuxd;
3. finds `05ac:12a8` and calls `dev.reset()`;
4. if reset fails, retries `set_configuration(3)` four times;
5. starts usbmuxd and checks `usbmux list` for the UDID.

`dev.reset()` is the reliable recovery. If `set_configuration(3)` returns
`Resource busy`, retry after a short wait; if the device is not on the USB bus
at all, the host cannot reset it — wake/unlock the phone, tap **Trust**,
replug the cable, and repeat.

Manual equivalent if the script is unavailable:

```sh
sudo -n systemctl stop usbmuxd
# pyusb: usb.core.find(idVendor=0x05ac, idProduct=0x12a8).reset()
# fallback: dev.set_configuration(3), up to 4 tries
sudo -n systemctl start usbmuxd
sleep 5
$VENV/pymobiledevice3 usbmux list
```

If it still fails: `doctor`, `lsusb`, pairing records under
`/var/lib/lockdown`, and the physical steps. A network `_rdlink` device is not
a substitute unless its UDID/model is the 17e.

USB can drop again mid-run. Recover **before each launch/pull**, and never run
two phone operations concurrently.

## 4. Delivery

Stock 17e delivery is Bot API `sendWidget`; the Postbox `t7` rewrite and
`appGroupDataContainer` are unavailable for the stock app.

### Bot selection

The bot is selected by the **token**, not by a bot-specific flag. The repo
sender is generic:

```sh
BOT_TOKEN="<token of the bot that owns the target chat>" \
python3 bot/send_widget.py \
  --html lab/ios17e/reliability_20261109/out/v10_primary6.html \
  --chat-id <CHAT_ID>
```

- The `@<BOT_USERNAME>` vs `@<BOT_USERNAME>` distinction did **not** discriminate for
  v10: both produced blank/stopped/parser-death without stage A. The bot is not
  the current variable.
- The lab helper
  `telegramandroidwidget/lab/artifacts_20261108/ios17e/send_widget.py --wasd`
  is a **lab-only shortcut** that scrapes a token from a local probe file; it
  is not the generic repo interface. Do not commit bot-specific flags or
  tokens.
- The target chat is the account's chat; the bot identity is whatever token
  owns it. Test the page, not the bot label.

```sh
# generic sender; no bot name/flag in the command
BOT_TOKEN="<token>" python3 bot/send_widget.py \
  --html <payload.html> --chat-id <CHAT_ID>
```

- Each call creates a new message id; same-id seed/final designs cannot use
  two `sendWidget` calls.
- Payload must be the **last** message; chat at the bottom; one payload per
  open.
- Delete old payload messages before a run. Old widgets in history re-render
  on open and can fault the process before the new one runs.

## 5. Cleanup is a hard gate (mandatory)

The chat must be clean **before every send and after every read**. Old widget
payloads re-render on open and can crash/stop the app before the new message;
one old payload is enough to invalidate a run. This is a user rule, not an
optional step.

- Delete the previous payload message(s) and any anchor/text sent for
  navigation with the bot that sent them (`deleteMessage`, bot token).
- Verify the chat has no old widget payloads left (screenshot/chat list, and
  the send log ids).
- Record the deleted message ids in the attempt log.
- A run in a contaminated chat is **not a data point**; discard it and clean
  again.
- Cannot delete a message (too old/not found)? Stop and report the exact id;
  do not measure in that chat.

Generic deletion (no bot-specific flag; token selects the bot):

```sh
BOT_TOKEN="<token of the bot that sent the message>" \
CHAT_ID="<chat>" MESSAGE_ID="<id>" \
python3 - <<'PY'
import os, urllib.request, urllib.parse
tok=os.environ["BOT_TOKEN"]; chat=os.environ["CHAT_ID"]; mid=os.environ["MESSAGE_ID"]
data=urllib.parse.urlencode({"chat_id":chat,"message_id":mid}).encode()
print(urllib.request.urlopen(f"https://api.telegram.org/bot{tok}/deleteMessage", data=data).read().decode())
PY
```

### 5.1 Crash counter and the 2-crash stop latch (official)

Official source: Telegram Widgets guide, "Lifecycle" section
(https://core.telegram.org/bots/widgets#lifecycle) and the "Limits" table
(https://core.telegram.org/bots/widgets#limits, row "Crashes: 2 in a row").
A widget that goes past a limit or crashes is stopped: its last frame stays
with a "Widget stopped" badge, and the app rebuilds it when it is shown again.
**After two crashes in a row it stays stopped until the app restarts.**

Operational rule for every run:

- Count consecutive widget/app crashes across attempts.
- After **2 in a row**, restart the app (relaunch) before the next attempt. Do
  not send another payload into a stopped bubble.
- A stopped bubble observed after two crashes is the stop latch, **not a new
  data point**: discard it, restart the app, and re-run from a clean chat.
- Reset the counter only after a run that renders and completes normally.

## 6. Host instrumentation

| Channel | Command | Use |
|---|---|---|
| App stdout | `$VENV/pymobiledevice3 developer core-device launch-application ph.telegra.Telegraph --console --userspace` | `RESULT`, `HIT=`, `ABV`, `N17E`, `js_free_rt:`, parser/endgame output. |
| Screen | `... core-device screen-capture screenshot <png> --userspace` | Visual marker/`#v`, chat state. |
| HID | `... core-device universal-hid-service tap|drag|type ... --userspace` | Tap coordinates, drag/back, text entry. |
| OCR | `$VENV/python docs/instrumentation/ios17e/ocr_screenshot.py <png> [--grep ...]` | Read marker/chat text. |
| Navigation | `$VENV/python docs/instrumentation/ios17e/navigate_chat.py <cmd>` | `open <text>`, `openbot`, `drag`, `tap`, `read`, `state`. |
| Proof file | `$VENV/pymobiledevice3 backup2 --only-regex '<APPGROUP>.*rce.txt'` | Authoritative `rce.txt` (23 s). |

Notes:

- `launch-application` defaults to killing an existing instance; use
  `--no-kill-existing` when the app is already warm. Do **not** use DVT
  `launch --stream` for normal runs: it kills the app when the stream detaches.
- `navigate_chat.py tap`/`drag` uses `universal-hid-service`; coordinates are
  in the 1170×2532 screenshot space and normalized to 16-bit internally.
- `run_sweep.py` automates: delete previous message → send → screenshot/OCR
  marker → on SpringBoard crash delete/relaunch → `nav.openbot()`.
- The proof file path contains the account-specific AppGroup id
  (`<APPGROUP>`); keep the real value in the lab, not in the repo.

## 7. Chat scrolling and render — the known hard part

Telegram restores the **last scroll position**. New widget rows are inserted
at the bottom. If the widget bubble is below the fold when the app opens, the
widget is not laid out and the page does not execute; the run produces no
marker even though `sendWidget` succeeded.

Consequences:

- `launch-application` does not scroll to the bottom; `--no-kill-existing` is
  not a scroll operation.
- CoreDevice HID can tap/drag, but a blind drag is not a reliable
  scroll-to-bottom: chat length, bubble height and current offset are unknown.
  `navigate_chat.py` can search/open the bot chat and verify the header, but it
  does not guarantee the payload row is visible.
- WDA (`developer wda ...`) is the full-autonomy fallback for scrolling and
  tapping, but it needs a dev-signed WebDriverAgentRunner that is not
  installed on this host/device.
- The reliable workaround is operator-assisted: open the bot chat, scroll to
  the bottom **before** the run, keep the payload as the last message, and do
  not move the chat between send and render. After a relaunch, repeat the
  scroll-to-bottom check.
- The successful 16:27 message was **below the fold**; its own stage-A marker
  was never captured. A missing screenshot marker is an instrumentation gap,
  not necessarily a failed run. Use the console and `rce.txt` as the
  authoritative channels.
- Old payload widgets in the chat can re-render and run; keep the chat clean
  and one payload per open.

## 8. One P1 run (v10)

Payload: `lab/ios17e/reliability_20261109/out/v10_primary6.html`
(8,647 raw / 3,647 zlib9 / sha256
`86c3a2751bc0a180d7cccda8e743f36d00c7738e4700083a7c16cf25d7f252ea`).
Baseline control: `out/v0_p0.html` (byte-identical to the proven page).

```
0. If the last two attempts crashed in a row, restart the app (§5.1). Delete
   the previous payload/anchor; verify the chat has no old widget payloads.
1. Recover USB if usbmux list is empty; wake/unlock/Trust.
2. Bot chat at bottom; app warm.
3. Attach console; note the log offset.
4. Send v10 (last message).
5. Screenshots at 0.6-4 s, then 5 s and 10 s.
6. Console tail from the offset.
7. backup2 --only-regex '<APPGROUP>.*rce.txt' (23 s, after the render).
8. Delete the payload message; record the id; clean before the next attempt.
```

Record per attempt: variant, t_send, first marker (`HIT`, `R`, `M`, `PH`,
`NT`), app alive/dead, console line (`js_free_rt:` / `N17E`), `rce.txt`
yes/no, cycle time.

Success: `rce.txt` = 7 B `RCE_OK\n` sha256
`704984d9d94917e9108dd47ee93714cad1b150078dfd36e828182fe0d82eed07d4`,
app alive; or the marker plus console endgame.

Failure classes:

- `HIT=-1` → safe miss; keep the app.
- no marker + app dead → parser fault; count the crash, relaunch, retry
  (after two in a row restart the app first, §5.1).
- forge + `U_NF`/`NO_*` endgame guard → stop and report; the geometry/endgame
  is the defect, not the transport.
- no marker + app alive → scroll/chat state or render gap; verify the chat is
  at the bottom and the widget is the last message.

Statistics: 10/10 → 95% lower bound 0.741; 30/30 → 0.905 (one-sided
Clopper-Pearson; the certification docs quote two-sided bounds: 30/30 →
0.884, 36/36 → 0.903 — state the convention wherever a bound is quoted);
≥99% success at 95% confidence needs ~300 clean runs (rule of three).
Report the point estimate and Clopper-Pearson bound.

## 9. Troubleshooting

| Symptom | First action |
|---|---|
| `usbmux list` empty but `lsusb` has 05ac:12a8 | `usb_recover.py`; wake/unlock/Trust; retry. |
| `Device is not connected` from CoreDevice | USB dropped; recover before retrying. |
| `ModuleNotFoundError: rapidocr_onnxruntime` | Use `$VENV/python`, not system Python. |
| Widget not visible / no marker | Chat not at bottom, old payload above fold, or render gap; scroll to bottom and re-send as last message. |
| **2 crashes in a row → widget stays stopped** | Official (Telegram Widgets guide, Lifecycle/Limits): the widget stays stopped until the **app is restarted**. Count consecutive crashes; after two, relaunch the app before the next attempt (§5.1). A stopped bubble after two crashes is not a new data point. |
| App crashed with no marker | Parser fault; relaunch and repeat with a clean chat. |
| Forge but no `rce.txt` | Endgame guard; capture `U_NF`/`NO_*` and console; stop variant switching. |
| `backup2` fails | USB link; recover, retry; backup is off the critical path. |
| Wrong device/model in `usbmux list` | Stop; confirm `iPhone18,5` + UDID; do not use the 6s/mDNS. |
