# Critical review of `tg-rce` (2026-11-08)

Reviewer role: demanding external reviewer. Scope: the whole sanitized tree at
commit `7a98fcd`, plus the campaign notes needed to check its claims. No device,
bot or network action was taken for this review. The only network action is the
repository SSH check.

Method:

1. Read every top-level index, every per-ID README, the two-phase docs, the
   handoffs, the payload READMEs, the bot and builder sources, and the evidence
   records named by those documents.
2. Recompute raw size, zlib9 size and SHA-256 for the canonical payloads with
   Python 3.13.5 / zlib 1.3.1.
3. Run the in-repo self-checks (see section 8).
4. Compare claims against the device records in the tree and against the live
   notes in the lab tree. Label anything that is not backed by a record.

The review found real device results and a strong parser primitive. It also
found status contradictions, a package-path bug that invalidates the Android
two-phase device claim, a newly measured Android isolated-process boundary
that changes the impact on beta 72979, a disproven desktop gate, and a
reproducibility layer that does not rebuild the shipped pages. The repository
is not ready to be read as a self-contained, reproducible archive until the P0
items are closed.

The single most important correction: **the Android impact is build-dependent.**
On beta 72889/72929 the widget runs in the app process (UID 10346), and the
c2560s route is an app-level RCE with a 185 B proof and a C2 as UID 10346. On
beta **72979** the widget moved to isolated UID 99017 (`u:r:isolated_app:s0`).
The parser stage A still works (`ABLEN[599]=327744 ATT=1`), but the endgame
stops at `HF ERR NOANCHOR VNC=0 VO=-1`, and the isolated process has no
app-private data access and no network permissions. On 72979 the parser bug is
contained code execution or DoS in the widget process, not app-level RCE. The
current beta **72989** keeps the same model: isolated UID **99024**,
`u:r:isolated_app:s0`, PING works, v3 detector `el=55ms`, v3 final
9,190 / 4,081 zlib9, same `HF ERR NOANCHOR`, no `n1`/C2, app alive.

The Android two-phase path is still not device-proven. The repo page writes the
release package path; the tested Sony app is the beta package. A beta rebuild
on 72929 hit stage A and then stopped at `HF ERR NA`. On 72979 the additional
isolation boundary blocks the same write. That is a stage-A success plus
endgame failure, not an RCE.

The desktop gate is not a security boundary. Real Telegram Desktop (Windows)
and the Sony widget sandbox both report `maxTouchPoints=0`, the same UA and
platform, and overlapping DPR and screen values. The old safe-area/DPR gate
passes both. The `maxTouchPoints > 0` gatefix blocks both. Account isolation is
the only reliable boundary.

### P0-02 The Android two-phase device claim is invalid

Files:

- `payloads/two_phase/final_inline.html:1` contains
  `org.telegram.messenger/files/n1`.
- `bot/platforms.json` correctly lists both package paths.
- `docs/STATE_20261108.md:20` calls the Sony two-phase row a device target.
- `docs/HANDOFF_ios27_two_phase_20261108.md:24-25` calls the Android pair
  unchanged.

Evidence from the live run (orchestrator record, 2026-11-08):

- The beta rebuild is 9,190 raw / 4,071 zlib9 (sha256 `8b8ccc13…`), 5 bytes
  longer than the repo release page.
- On the Sony beta 72929, the detector reported in 63 ms, the host sent the
  final in 145 ms, the final rendered in 74 ms.
- The final hit stage A and then the endgame returned `HF ERR NA`.
- The app stayed alive and no proof file was written.
- On beta **72979** (post-commit update) the same package hit stage A
  `ABLEN[599]=327744 ATT=1`, then the endgame returned
  `HF ERR NOANCHOR VNC=0 VO=-1`; no `n1`; app alive. The widget runs in
  isolated UID 99017 (`u:r:isolated_app:s0`). The isolated process has no
  app-private data access and no network permissions, so the app-data write
  and C2 are blocked even after an anchor fix.

Why the path matters: the endgame writes the proof with the path in its
command string. The repo string points at the release package
`org.telegram.messenger`; the installed app is
`org.telegram.messenger.beta`. Even if the anchor resolved, the write would
target a non-existent directory for that UID, or be denied. The repo payload
cannot produce the beta proof. On 72979 the isolated UID adds a second
blocker: it cannot write the app-private path at all.

Impact: the two-phase Android path is not device-proven. The stage-A hit is
real and useful, but the endgame failure is not a reliability number. The
72979 result is contained code execution or DoS in the widget process, not
app-level RCE.

Recommendation: do not change the payload in this commit. Add a `--pkg beta`
build artifact with its own hash, and run the anchor fix on the beta package.
Until then, label the two-phase Android path "stage A device-proven, endgame
device-failed (`HF ERR NA` on 72929; `HF ERR NOANCHOR` on 72979); 72979
contained". App-level Android proof requires 72929/72889 or an isolated-process
escape.

Status in this commit: documented in README, STATE, PLAN, the two-phase doc
and the handoff. The payload bytes are unchanged.

### P0-03 The desktop gate is not a boundary

Files at the reviewed commit:

- `docs/HANDOFF_desktop_gate_20261108.md:1-5` ("merge-ready", "no-op on
  Telegram Desktop").
- `docs/two_phase_universal_20261108.md:723-848` (the full gate claim).
- `payloads/two_phase/detector.html:1` and `final_inline.html:1` (old
  safe-area/DPR gate).
- `payloads/two_phase/ios27_gated/final_ios27.html:3` and
  `ios15_gated/at_final_h400.html` (same old gate).

Measured facts:

| Environment | `maxTouchPoints` | Old gate | `MT>0` gate |
|---|---:|---|---|
| Telegram Desktop (Windows) | 0 | passes (DPR 2.0) | blocks |
| Sony XQ-BT52 sandbox | 0 | passes (DPR 2.6) | **blocks the target** |
| iPhone 6s / 17e | not a discriminator | passes | passes/fails by device |

The UA and platform strings are the same shared `TelegramWidget` strings. The
pointer is fine on both. A JS gate that uses these fields cannot separate the
real desktop client from the phone sandbox.

The old gate's desktop behavior was observed: the detector reported
`platform=9 ... dpr=2.0 scr=430x300`, and the host skipped the final. That is
a host-side policy, not a payload stop. A final opened directly would execute
stage A.

Impact: the repository claimed a safety property it does not have. A payload
opened in Telegram Desktop can run the same code and produce a crash report.

Recommendation: retract the claim, keep `platform=9` as an operator guard,
and use account isolation. Do not add another JS heuristic and call it a
boundary.

Status in this commit: the handoff is rewritten as a withdrawal; the
two-phase section is rewritten; README and STATE no longer claim desktop
safety. The payload bytes are unchanged.

### P0-08 The Gitea remote may still hold pre-scrub objects

The local history is a single root commit (`7a98fcd`). `git ls-remote` shows
only `refs/heads/master` at that commit. That proves the refs, not the object
store. A normal push does not delete unreachable packs. The old pack can
remain on the server until Gitea runs a GC or the repository is recreated.

Impact: secrets that were removed by the rewrite may still be recoverable from
the server side.

Recommendation: recreate the repository from the sanitized tree, or run the
Gitea GC/archive procedure and verify with a fresh clone plus
`git fsck --unreachable`. This review cannot perform that server-side action.

Status in this commit: documented as a residual risk; no server change.

### P0-09 Parser offset arithmetic was inconsistent

At the reviewed commit:

- `vulns/0day-2-RCE-PARSER-SCOPE/README.md:127` said
  `b->arg_count + 65534` x 20 = `1,310,680` past `b->vardefs`.
- The same line said `1,310,700 from b`.
- The evidence report said `+1,310,680` in one place and `1,310,700` in
  another.

Correct arithmetic:

- `arg_count = 1`, index `= 1 + 65534 = 65535`.
- `65535 * 20 = 1,310,700` bytes past `b->vardefs`.
- Android `vardefs = b + 128`, so the target is `b + 1,310,828`.
- iOS `vardefs = b + 0x2A0 = b + 672`, so the target is
  `b + 1,311,372`.

Impact: a reader cannot reproduce the target address from the text. The route
docs use the correct `b + 1,310,828` and `b + 1,311,372`, so the error is
localized but embarrassing in the bug report.

Status in this commit: corrected in the ID README and the parser report.

### P1-03 Zlib margin

The gated Android final is 28 B under the limit; the beta rebuild is 25 B
under. A one-line comment in the gate can overflow. `send_widget.py` now
checks raw and zlib sizes before connecting, but a browser-side builder can
still produce an over-limit page.

Recommendation: the generator must fail closed at 4,080 B (16 B reserve), not
at 4,096. The current generator asserts only the hard limit.

### P1-04 17e gated twin

The gated twin is 9,139 B. The proven page is 8,647 B. The extra prefix and
wrapper change the pre-heap. The 17e has a teardown abort whenever a forge
does not exit the thread, so a failed twin is not a safe miss.

Recommendation: treat any 17e gated page as a new shape. Do not send it
without a fresh stage-A measurement and a planned `pthread_exit`.

### P1-05 6s attribute final

`payloads/two_phase/ios15/at_final_h400.html` is 6,801 / 2,528. The handoff
calls it host-validated/device-pending. The proven 6s RCE used the storage
seed plus `inline-rop-h200.html`, not this attribute final.

Recommendation: keep the proven path as the default; do not describe the
attribute final as a drop-in replacement.

### P1-06 5725 evidence

The repository records the `rce.txt` hash but not the screenshot burst, the
console log, or the message metadata. The marker provenance correction is
good, but the proof is still a text claim.

Recommendation: add redacted screenshots and the relevant console lines, or a
signed evidence bundle with hashes. Do not add the raw chat.

### P1-07 6s evidence
