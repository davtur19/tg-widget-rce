## What the construction does

* s0 installs the InternalError name getter, creates `O` (1023 props), fills
  the class-128 arena with **200 wide marker strings** (47 code units,
  `String.fromCharCode`, request 118 → class 128). Every marker encodes at
  object offset 108 the value the negative scope walk reads as
  `scopes[-1].parent` (−1 for probe 2, −2 for probe 3) plus the rest of the
  chain at 88/68/48; a 4-byte tag sits at object offset 100 (block 108) and a
  write watch at object offset 112 (block 120).
* The fill script schedules J2 and then runs the self-calibrating class-48
  fill to the OOM (the getter keeps the run alive).
* J2 `TAKE(6720)` exact-class coins, pumps 6 class-48 strings, **pops the last
  two markers** (creating a two-block free run), pushes **one guard marker**,
  and evals the N1 source. The eval's 4→6 scopes grow takes the block after
  the guard, so the block before the scopes is always a controlled marker.
* The failed 6→9 `push_scope` makes the parser walk `scopes[0] -> -1`; the
  encoded parents keep the walk at −1 (probe 2) or drive it to −45 (probe 3).
  Probe 2's final add writes `idx=134` at `scopes−16` (chars 44..45 of the
  block before the scopes). Probe 3's add writes at `scopes−896` = the
  `JSString.len` of the block seven before the scopes.
* The marker script reads every marker back: probe 2 reports which marker's
  `charCodeAt(44)` changed; probe 3 reports whose `.length` changed.

## Sony DB test sequence (orchestrator)

The DB delivery is the existing `lab/qjs_n1/device_run_sony_subagent/run_probe.sh
<run_name> <html_path>` path (Sony XQ-BT52, beta 72929, uid 10346), one payload
at a time, with the USB link recovery described in the project rules.

1. **Probe 2 first.** `run_probe.sh p2marker widget/n1_p2_marker_selfloop.html`.
   Expected: the widget text and the logged exception carry
   `P2 NB=1 BAD=<idx>:86 W=86 I=<idx> N=199`; the app stays alive.
   * `NB=0` = the eval completed without the gate (F too low for the device
     parse cost) or the gate fired elsewhere; app alive, no data. Do not retry
     blind; report the value and stop.
   * Crash = the k=0 residue (the marker run ended at a page boundary); report
     the fault and stop. A retry with `N=201` shifts the residue by one block
     (`gen_p23.py p2 6720 201 2 0 0 ...`), but only after the crash is
     confirmed as the k=0 case.
2. **Probe 3 only after a safe probe 2.**
   `run_probe.sh p3leak widget/n1_p3_marker_leak.html`.
   Expected: `P3 NB=1 TLEN=134 BAD=<idx>:134 I=<idx> N=199`; app alive.
   A `TLEN=134` is the leak hit (a string length grew from 47 to 134).
   `NB=0` = a mapped miss (the target fell outside the marker pages); app
   alive; report it, do not retry blind.
3. **Pixel bot only after a safe Sony `TLEN=134`.** The same
   `n1_p3_marker_leak.html` (1,253 zlib9) is within the bot limit. The N1
   arena is tag-0 (the fork's own mmap arena, §8.3), so the cross-block write
   at `scopes-16` carries the same tag as the marker block and is MTE-safe in
   the tag-0 model; this is a model statement, not a Pixel measurement. The
   Pixel endgame still needs the v7 resolver once the AB target is added.

## Residual risk (documented, not hidden)

The free-run construction puts the scopes at block `b` where `b` is the block
of the last marker before the two pops. If `b = 0` (the marker run ends exactly
at a 4 KiB page boundary), the scopes is block 0 of the next page and the
first negative pop reads the arena header instead of a marker. This is the
only unsafe configuration. Host N sweep 180..220: exactly one bad N (203, 3/3
crash), all others hit; ~1 crash in 70 ASLR-on runs of the delivered N=200,
0/80 with ASLR off. `N+1` shifts `b` by one block.
