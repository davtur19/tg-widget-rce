## Bug

- Finding 3 is the `await using` parser chain; finding 4 is the
  **generator `var_refs[]` OOB**: `async_func_init()` heap-allocates the
  generator frame, bypassing the 1 MiB JS stack limit; duplicate parameter
  names + runtime source generation fit the 8 MiB widget heap;
  `js_closure2()` walks `sf->var_refs[]` past the frame.
- 10/10 SIGSEGV at 8 MiB/1 MiB/500 ms; ASan
  `heap-buffer-overflow READ of size 8` at `get_var_ref quickjs.c:17729`.
  The C=1 indirect-eval variant survives 10/10 and performs a silent OOB
  write into the next malloc chunk's `prev_size`.
- Device C1 death explained: the page pre-zeroed `R+8`, but the OOB slot is
  at `arg_buf+R`; the **`R+24` shape** (the freed block's 16-byte tail)
  covers the OOB word and is script-controlled.
- Heap chain: 64-bit heap leak → victim `JSString*`/`ArrayBuffer` →
  fake-var-ref strings → 16-byte JSValue write at any known address →
  victim SLICE header (`len=0x7FFFFFF0`, `slice.parent=Q-24`) →
  `charCodeAt(i)` reads `*(Q+i)`; restore the header. Host 10/10.

## Content fault and BUF fix (post-ARM)

The wrong bytes were not a stale account path alone: `isambiguate…` is a
string in **TelegramUIFramework**, and `sptk` uses the account-independent
`accounts-metadata/login-tokens` path. The old chain's
`mmap(MAP_FIXED, 0x300000000, 1 MiB, RW, 0x1012, -1, 0)` did not produce a
private read/write buffer on this app; the fixed address aliased an existing
framework page (read-only/rodata). The chain ignored the `mmap`/`open`/`read`
returns, so `read` left that page and `write` copied it to `spdb`/`sptk`.
The stale `account-6530317337104534560` is a DB-only risk; it cannot explain
the identical wrong `sptk`.

Fixed pages:

| page | bytes | zlib9 | sha256 | purpose |
|---|---:|---:|---|---|
| `f4_session_tokens_buf.html` | 6,902 | 2,888 | `60ee6676…61b59` | BUF, tokens-only, account-independent |
| `f4_session_file_buf.html` | 7,094 | 2,935 | `56f2d82d…ba52` | BUF, DB + tokens, current account |

Both remove `mmap` and use `BUF`, the data pointer of a live, zero-initialized
1 MiB `Uint8Array` (`JSObject.u.array.ptr`, `RB+56`), prefilled with
`F4READFAIL`. Destinations are `spdb.raw`/`sptk.raw`; a failed open/read
leaves the sentinel and cannot overwrite the old false `spdb`/`sptk`.
